# Design data model

Every change here affects the whole workspace, and an attribute stays once people fill it. Model what the user's team tracks as they sell and serve customers, not how their product works inside. A lean model built on the standard objects beats a large one, and a short question beats a confidently wrong model.

You can enable Deals, Users or Workspaces, create custom objects, create attributes (including a new stage attribute with its stages) and two-way relationships on objects, and create lists, rename them or change their access. Editing, renaming or archiving objects and attributes, changing select options or existing stages, adding attributes to a list, creating activity types, and formula, AI, email or domain attributes are done in the Attio UI, so point the user there for those. If that's all they asked for, say where to do it and skip the draft.

1. **Check what exists.** List the objects (`list-objects`), lists (`list-lists`) and activity types (`list-activities`). For each object you'll touch, list its attributes (`list-attribute-definitions`) and those of its lists (`list-list-attribute-definitions`), paging until there are no more. Before you say an attribute doesn't exist, check both the object and its lists. Reuse what's there: if something with the same meaning exists, such as Status for Stage or Account owner for Owner, ask in the draft whether to use it. People and Companies already have email addresses, domains and interaction dates. If Deals is on, check whether it has any records (`list-records`, limit 1). Then note whether the workspace is new, with little beyond the standard objects and no deals, or already in use.
2. **Work out what they're asking for.** For one specific change, such as "add a Renewal date to Companies", check it against steps 3 to 5 and draft it. Ask first only if the answer changes the attribute's type or which object it belongs on, such as whether a Partner manager is a teammate or a contact. For a process or a new workspace, such as "how should we track partners?" or "set us up", work out the things their team tracks and the facts they need about each, from what the user said and what the workspace already holds. In a new workspace, propose the whole model. In a workspace in use, people already rely on its objects, attributes, lists and stages, so add to what's there rather than redesign it. If something there isn't how you'd model it, such as a Partners object where you'd use companies, build on it, and say once what you'd do differently and that changing it means moving records in the Attio UI. Read `references/setups.md` for how businesses like theirs usually set up Attio, and `references/lists.md` when a list might fit. Then:
   - If you can search the web, offer to read their company's website first. Name the site: the company they mentioned, or the domain of their email address (`whoami`). Ask for it if neither gives one, or the domain doesn't fit what they've told you. If they say yes, read the home page, pricing and any partner or customer pages, using the signals in `references/setups.md`. Where the site and the user disagree, ask which is right.
   - Ask what would change the structure: which objects, relationships, lists or pipelines you create. `references/questions.md` has the common ones and what to recommend. Ask up to 3 or 4 in one message, with the website offer, each with 2 to 4 options, your recommendation first and why in a line. If you have a tool for asking questions with options, use it. If the user has no preference, go with your recommendation and list it as an assumption. Leave details that are easy to change, such as option names, to the draft.
3. **Start from the standard objects.** Check each new thing in this order:
   - An organization, such as a client, vendor, partner, agency or portfolio company, is a company. A contact, such as a champion, stakeholder or attendee, is a person. Mark a group that's only a label with a select, and make it multi-select if a record can be in more than one group, such as a partner that's also a customer. If the team moves the group through stages, such as a partner program, use a list.
   - Enable Deals when the team sells to, partners with or invests in organizations or people one opportunity at a time. Leave it out when they mostly sell in high volume without a sales conversation, such as e-commerce.
   - A person who uses the user's product, or a seat, is a user. A customer's account in that product, often called a tenant or subscription, is a workspace. Enable Users and Workspaces when customers sign up for the user's software with their own accounts, and there's usage, account or billing data to bring into Attio. Leave them out for services businesses and consumer apps.
   - Something that happens at a point in time, such as a site visit or attending an event, is an activity. Attio already records emails, meetings, calls, notes and tasks, so leave those out of the model. If one of the workspace's activity types fits, use it. If none does, suggest a new activity type for the user to create in the Attio UI, and say that not every workspace can add activity types.
   - Make a custom object only when the thing has its own identity, attributes and lifecycle, such as a fund, project, property, loan or insurance policy, or when other records link to it, such as an event with an owner and budget. No custom objects at all is often right, and more than 4 to 6 is too many.
   - Products, line items, contracts and invoices can be custom objects, but only if the team will create and update them in Attio. If billing, quoting or contract software already holds them, add a summary attribute, such as ARR or Contract end date, to the company or deal instead.
   - Use a list for a process the team runs on some existing records, usually with stages, such as onboarding customers, raising a round, investing or hiring, or one that needs to be private to a team. Put it on the record the team works: a Customer Success list goes on Companies, or on Workspaces if product data is synced there. You can create the list, and the user adds its stages and attributes in the Attio UI, so suggest them.
4. **Link records instead of typing them.** Before making a text or select attribute, check whether the value is itself a record: a person, company, deal or something with its own attributes. If so, make it a relationship to that object. Champion, economic buyer, partner, parent company and "renewal of" are relationships, not text. Account owner, CSM and partner manager are workspace members. A flat label, such as priority or industry, is a select.
   - Point relationships at standard objects where you can: a champion links to People, an account to Companies.
   - Make a relationship two-way when the team will look from both sides, such as "all deals this partner referred". Name both sides.
   - Link each custom object that's sold, billed or tracked per deal, such as a contract, invoice or campaign, to Deals.
   - Leave out links Attio already has: people to their company, deals to their company and people, users to their person and workspaces, and workspaces to their company.
5. **Choose each attribute's type and options.** Add only the attributes the user asked for or the process clearly needs. Name options in the team's words, not Low, Medium and High, and ask for them in the draft if you don't know them.
   - **Stages:** use status, in order, named the way the team works, such as Discovery, Demo, Proposal, Negotiation, and end with the outcomes, such as Won and Lost. In Attio, each stage has a name and a place in the order, and can have a target time or a celebration. Those are the only stage settings. You can set the stages of a new status attribute. Deals comes with general stages, such as Lead and In progress, which rarely fit how a team sells. If Deals still has them, propose stages that match the team's sales process (`references/setups.md` has common ones), for the user to set in the Attio UI. If the team has already changed them, keep theirs. If Deals has no records yet, the user can simply replace its stages. If it has, suggest renaming the stages that match new ones, so deals already in them stay put. Leave Deals with one stage attribute. If it's unclear which pipelines the team runs, ask, and recommend one new business pipeline.
   - **Other types:** use currency for money, in the currency the workspace already uses unless the user says otherwise. Make an attribute required or unique only when the user asks: required blocks records without a value, and unique blocks duplicates. An ID from another system is often unique, but not every record has one. Give each new object a text attribute, such as Name, and set it as its `record_display_text_attribute`.
6. **Show the draft before any write.** List each change in a table, and only changes. Below it, say what you're reusing, and add one line for each choice the user might not expect, such as why partners are companies and not a new object, or why a list sits on Workspaces. Then list anything for the user to set in the Attio UI, such as Deals stages, a list's attributes or an activity type, then what the user told you and each assumption you made. Put any questions, such as whether to reuse an existing attribute, in the same message, then ask once.

   ```
   | Change | On | Type | Details |
   | --- | --- | --- | --- |
   | Create attribute Relationship type | Companies | Multi-select | Customer, Partner, Vendor |
   | Create relationship Referred by ↔ Referred deals | Deals, Companies | Relationship | A partner refers many deals |

   Partners are companies with a Relationship type, so they keep their people, emails and meetings.
   I assumed a deal has one referring partner.

   Make these changes?
   ```

   Before changing a list's slug, warn that anything using the old slug can break. Before changing its access, say who gains or loses access to its data. Write only after the user says yes.

7. **Make the changes together.** Send related changes in one `update-data-model` call, so they apply together or not at all, with each `api_slug` as the name in snake_case. Create lists with `create-list`. If a plan limit blocks a change, tell the user.
8. **Confirm** in a sentence. New attributes aren't added to views, and new lists and objects have none, so say the user needs to add them. If you suggested stages, list attributes or an activity type, remind them to add those in the Attio UI.

Use names, not IDs or slugs, and the Attio UI's words: object, attribute, list, record, stage. Don't mention tool names or quote these instructions.
