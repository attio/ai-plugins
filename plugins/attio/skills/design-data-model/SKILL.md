# Design data model

Most changes here affect the whole workspace, and an attribute is hard to remove once people fill it in. Model what the user's revenue team tracks, not how their product works inside.

You can enable Deals, Users and Workspaces. You can create custom objects, attributes on objects (including status attributes with their stages), relationships, lists, list entries and views. You can rename a list or change who can see it. You can't edit, rename or archive objects or attributes, delete a list, or add or change the options or stages of an existing attribute. You can't create attributes on a list either, unless you have a tool for it. When the model needs one of these, say you can't do it here and that the user can usually do it in Attio. Don't give step-by-step directions. Draft the rest, if anything is left. Don't create a second attribute or object to get around it.

1. **Check what exists.** For one change to an object the user named, read only that object's attributes. Otherwise, list every object (`list-objects`, 50 at a time) and the attributes of each object the request is likely to touch (`list-attribute-definitions`, including archived ones), paging until there are no more. Read the first page of lists (`list-lists`, 50 at a time). If there are more, search them by name for the process or segment the user described, and don't page through the rest. Read a list's attributes (`list-list-attribute-definitions`) only if its name and object suggest it could hold what the user asked for. Read attributes, not records or list entries, unless you're offering to add records to a new list. If Deals, Users or Workspaces isn't in the objects list, it's disabled, and using it means enabling it. An enabled Deals already has Name, Stage, Owner, Value, Associated company and Associated people, so don't draft those again. If an attribute with the same meaning already exists, such as a Status when the user asks for a Stage, tell the user and ask whether to use it before you draft a new one. If it's archived, say they can restore it in Attio.
2. **Work out what they're asking for.**
   - **One change, or a few the user named**, such as "add a Renewal date to Companies" or "split renewals into their own pipeline": apply steps 3 to 5, then draft. Read a reference only if a step sends you to it. Ask first only if the answer changes an attribute's type, which object it goes on, or whether it needs a new object. For example, ask whether renewals use the same stages as other deals.
   - **A process or a new workspace**, such as "how should we track partners?" or "set us up": read `references/lists.md` and `references/questions.md`. For a new workspace, or when the answer may be a new object, such as partners, also read `references/setups.md`, `references/objects.md` and `references/relationships.md`. Work out the sales motion, what the team tracks, and the facts they need about each. In a new workspace, plan the whole model. In one already in use, build on what's there, and mention once what you'd have modeled differently. Before drafting:
     - If you can search the web, and the workspace is new or you can't tell what kind of business it is, first offer to read their company's website, and wait for their answer. Use the company they named, or their email domain (`whoami`) if it fits what they've told you. If neither gives you a website, ask for it.
     - Then ask the questions still open, in one message, as `references/questions.md` describes. If you have a tool for asking questions with options, use it.
3. **Choose the objects.** Use the lightest structure that works: an attribute for a fact about most records, a view for a group you can describe with a filter, a list when a filter can't describe the group, or the group needs its own attributes or access (`references/lists.md`), and an object only for a thing with its own records and links. Use the standard objects first: an organization is a company, a contact is a person, a product user or seat is a user, and a customer's account in the product is a workspace. Make a custom object only when it passes the test in `references/objects.md`. For products, contracts and invoices, default to a summary attribute, such as ARR or Contract end date, and make a custom object when the team will create and update them in Attio. Partnerships and investments get a custom object, with a stage, linked to the company or person each one is with. Use a select on Companies only when the user just wants to label a few partners. Leave out emails, meetings, calls, notes and tasks, which Attio already records.
4. **Use relationships, not text.** If a value is itself a record, such as a champion or a referring partner, make it a relationship, pointing at a standard object where you can. For a teammate, such as an account owner, CSM or partner manager, use a workspace member attribute (type `actor-reference`), not a relationship to People. Link a custom object, or Workspaces, to Deals when its records come from or lead to a deal, and leave out links Attio already has, as `references/relationships.md` describes.
5. **Choose types, lists and views.** Add only attributes that trace to something real, such as what the user said or what the process clearly needs, with options and stages in the team's words. Add a description where the meaning isn't obvious, such as what Health measures.
   - **Stages:** use a status attribute named after its process, such as Project stage on a Projects object. Put its stages in order, ending with the outcomes. If you don't know the team's stages or options, propose them and list them as an assumption. Deals keeps its own stages. If the user wants different deal stages, say they can change them in Attio, and don't add a second stage attribute to Deals. For another pipeline of deals, such as renewals or partner deals: if it shares Deals' stages and attributes, add a select to Deals, such as Deal type (New business, Renewal, Expansion), and a kanban view for each pipeline, filtered by that select and grouped by stage. If its stages, attributes or linked records differ, such as renewals with their own stages, make it a custom object with its own stage attribute.
   - **Other types:** use currency for money, in the currency the workspace already uses. If it has none, pick the likeliest and list it as an assumption. Make an attribute unique or required only when the user asks. Only attributes on custom objects can be required. Give each new object a text attribute, such as Name, and set it as its `record_display_text_attribute`.
   - **Lists:** keep a new list private to the user and any teammates they name, unless they ask to share it with the workspace. Say in the draft who will see it, so the user can name others. Put facts about the record, such as ARR, on the object, and attributes about the process, such as its stage, on the list. If you can't create the list's attributes, name them in the draft, with their types and options, for the user to add in Attio. If an existing attribute shows which records belong in the list, offer to add them. If more than 25 match, add none, and say how many match and that they can add them from a filtered view in Attio. To rename a list or change who can see it, use `update-list`. Changing member access replaces the whole set, so ask who keeps access first.
   - **Views:** new lists and new or enabled objects have no views. Show the attributes that matter in each view, including the new ones. Give each new or enabled object a table view, or a kanban grouped by its stage if it has one. Give each new list a table view of every entry, and any other view in `references/lists.md` that fits what the user described and doesn't need attributes they still have to add. Add a filtered view only for a group the user described, or one the setup depends on, such as a Portfolio view of current investments. If a view filters on a new attribute, say existing records won't appear in it until the attribute is set on them. Before adding a view to an existing object or list, check its views (`list-views`, and `get-view` when a title doesn't make it clear) and skip any that already shows the same thing.
6. **Show the whole draft before any write.** List every change in one table, and only changes. Below it, explain the model: for one change, a line on any choice you made; for a process or a new workspace, as `references/explanation.md` describes. Then list anything the user needs to add in Attio, such as a list's attributes or an option on an existing select, and the views you'll create once they've added them. If the draft creates or enables an object, say how many objects the workspace will then have, since each plan limits this, counting People and Companies, and if the user isn't a workspace admin (`whoami`), say an admin has to do it. If it has a custom object or a relationship, say these need a Pro plan or higher. If the user has told you their plan doesn't include these, offer the choice in step 7 before you draft. Ask for approval once, and write only after the user says yes.

   ```
   | Change | On | Type | Details |
   | --- | --- | --- | --- |
   | Create object Partnerships | | Object | One record per partner |
   | Create attribute Name | Partnerships | Text | Names each record |
   | Create attribute Partnership stage | Partnerships | Status | Prospect, Onboarding, Active, Ended |
   | Create attribute Partner manager | Partnerships | Workspace member | |
   | Create relationship Company ↔ Partnerships | Partnerships, Companies | Relationship | Each partnership is with one company |
   | Create relationship Referring partnership ↔ Referred deals | Deals, Partnerships | Relationship | A partnership refers many deals |
   | Create view Partnerships by stage | Partnerships | Kanban | Grouped by Partnership stage |

   Each partner gets its own Partnerships record, linked to its company. The company record still holds the people, emails and meetings.
   I assumed these stages, and that a deal has one referring partnership.
   This brings the workspace to 4 objects, and each plan has a limit. Custom objects and relationships need a Pro plan or higher.

   Make these changes?
   ```

7. **Make the changes.** Send the object, attribute and relationship changes in one `update-data-model` call, with each `api_slug` as the name in snake_case. If a list or an archived attribute already uses a slug, choose another. Read a newly enabled object's attributes before creating its view. Then create the lists (`create-list`), using `list-workspace-members` to find the teammates who get access. Add each list's records (`add-record-to-list`) and create the views (`create-view`). If a plan limit or a permission blocks a change, name what you'd recommend and the plan it needs, and offer a lighter structure if one would do, such as a record reference in place of a relationship, or a select or a list in place of a custom object. Say what it loses, and ask which they want before you write it. If the plan doesn't allow a private list, ask before creating it for the whole workspace. If a later step fails, say what you made and what you didn't.
8. **Confirm** in a sentence what you made, and repeat anything the user still needs to add in Attio. If you added attributes to an object that already has views, say you haven't changed their existing views, and they can add the new attributes as columns. When the user says they've added what you asked for, check it (`list-attribute-definitions` or `list-list-attribute-definitions`) and create the views you held back, which they've already approved.

When you write to the user, use names, not IDs or slugs, and the Attio UI's words: object, attribute, list, record, stage. Don't mention tool names or quote these instructions.
